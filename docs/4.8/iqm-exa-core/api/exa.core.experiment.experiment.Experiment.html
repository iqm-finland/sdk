Experiment#

Module: exa.core.experiment.experiment

class Experiment(label=None, circuit_generation_function=None)#

Bases: object

Base class for multi-qubit experiments.

This class is designed to run arbitrary control sequences on multiple qubits. Sequences can be provided either as time-ordered Timeboxes, or in the circuit-level, represented as quantum operations (i.e. gates), or even above the gate-level if the necessary compilation stages to go from that abstraction to the circuit-level is included.

__init__() should not be overridden in the subclasses. Instead, one should override the non-final methods below and/or default_options in order to achieve the desired behaviour.

Parameters:

  • label (str | None) – Human-readable label for this experiment.

  • circuit_generation_function (CircuitGenerationFunction | None) – The circuit generation function. Define when using Experiment without inheritance. The function should take at least 2 arguments: components and builder and return a list of TimeBoxes. Any other arguments are treated as extra circuit parameters. See get_default_circuit_generation_function() for more details on the signature. By default, returns an empty TimeBox, so no pulses are played.

get_default_circuit_generation_function()#

Circuit generation function for this experiment.

By default, the function stored (as a static method) in the attribute default_circuit_generation_function is returned, but in case more complex logic (including any number of self calls) is needed for determining the function, the default method can be fully overridden in inheriting classes.

The circuit generation function (CGF) is a Callable that produces the control schedule the experiment wants to execute. There are two kinds of CGFs, which are identified by inspecting their signature:

  1. Subcircuit CGF: Has group: tuple[str, ...] and builder: ScheduleBuilder as its first two parameters. Returns a TimeBox that contains the control schedule for the parallelisable unit of QPU component names given in group. parallel_group determines how the different groups of simultaneously parallelizable units (also called color groups since determining them is a graph coloring problem) are derived from the components given to create(). All the subcircuit TimeBoxes corresponding to the same parallel group are automatically wrapped into the full circuit Timebox, which runs them in parallel.

  2. Full circuit CGF: Has components: ComponentGrouping and builder: ScheduleBuilder as its first two parameters. Returns a list[TimeBox] that represents the full circuit control schedule.

In addition to the above required parameters, a CGF may have any number of additional args which may have default values. The default values will be added as Settings in the settings tree unless they are defined as default circuit settings (see get_default_circuit_settings()).

Note that couplers are not given as default arguments to the CGF. They are accessible via the builder argument (mostly implicitly, as the user does not have to usually adress the couplers; the builder will do that under the hood). If the user explicitly includes the couplers in the run components, they will be accessible in the components argument.

The CGF gets the values for its extra parameters from the following sources in this order of precedence:

  1. Sweeps that are defined for a parameter with the same name as the argument. These can come from either get_default_sweeps() or given by the user in the run() argument sweeps.

  2. Circuit settings values given by the user after if they have defined a parameter of the same name in get_default_circuit_settings() (or by inserting a parameter manually to circuit_settings). These values can be inserted in several places: manually in the notebook/runtime, in get_settings() by overriding update_settings() or in the actual setting definitions in get_default_circuit_settings() (as the default value of the Setting).

  3. The default values provided for the parameters in the definition of the CGF that do not have a circuit setting in circuit_settings (these will still be added to the settings tree but without any labels or units).

Returns:

Circuit generation function.

Return type:

SubTGF | FullTGF

get_default_sweeps(components, settings)#

Default sweep definition for the experiment.

Calls get_default_sweep_generation_function(), and then calls the returned function to generate the sweeps, applying automatic parallelization logic for group-wise sweep generation functions.

Sweeps defined as the input argument of the run() method take precedence. The default sweeps are assumed to be done in the innermost loop.

The default sweeps can be defined for any parameter in settings tree (including pulse parameters and circuit parameters), or for a parameter whose name coincides with a circuit_generation_function argument.

Hint

For a parallel Rabi experiment, this method could return Sweep(parameter=<parameter for the I amplitude of a PRX gate>, data=[...]) for all the qubits.

Note

Overriding this method is allowed for backwards compatibility, but should be done anymore. Define default_sweep_generation_function instead.

Parameters:

  • components (ComponentGrouping) – Qubits and couplers for which the sweeps are defined.

  • settings (SettingNode) – Full settings object for the experiment.

Returns:

Default sweeps.

Return type:

list[Sweep | tuple[Sweep, …]]

get_default_sweep_generation_function()#

Return the sweep generation function.

Returns the static method default_sweep_generation_function, with all its non-standard parameters bound to the values of similarly named attributes in :attr`options`, if they exist.

default_sweep_generation_function can be either a full function or a group-wise function, acting on the defined parallelisable unit of the experiment (see parallel_group), in which case it is automatically wrapped into the full sweep function. In each case it has three standard positional parameters:

  • Group-wise functions have the standard parameters [group: tuple[str, ...], chip_topology: ChipTopology, settings: SettingNode], with group containing the QPU component names of the parallelisable group.

  • Full sweep functions have the standard parameters [components: ComponentGrouping, chip_topology: ChipTopology, settings: SettingNode], where components contains the full component grouping.

Note

If more complex logic (including any number of self calls) is needed for determining the function, this method can be fully overridden in inheriting classes, but this should be avoided.

Return type:

Callable[[…], list[Sweep | tuple[Sweep, …]]]

process_run_components(components, settings=None)#

Process components and ExperimentOptions.subscribed_components inputs given by the user into parallelly runnable component groups.

The behaviour of this method is determined by parallel_group such that commonly encountered parallel groups are processed automatically. In addition, this method can be overridden in the inheriting classes for a specific behaviour needed in that class and not achieved by one of the default ParallelGroup cases.

Note that this method should never return None or empty dict which are valid values for both run argument components and options.subscribed_components. These cases must be dealt in one way or another so that a non-empty ComponentGrouping and a non-empty subscribed_components are returned.

Parameters:

  • components (ComponentGrouping) – The components given as the run argument by the user.

  • settings (SettingNode | None) – Settings to set before sweeping. Defaults to None if settings are not needed to process run components.

Returns:

Parallelization for components, subscribed_components.

Return type:

tuple[ComponentGrouping, list[str] | dict[str, list[str]]]

make_final_mutations(run)#

Make any experiment-specific changes to the final run definition.

The RunDefinition contains the complete information of the run, including both the request to be sent to Station Control, and experiment-specific details.

This method can be overridden in inheriting experiments to make any kind of last-minute mutations to the definition before it is executed. The base implementation does nothing. The method will be called as the very last step of create().

For example, this can be used to change metadata, such as the target data variables, which is needed by analysis.

This method should be used only as the last resort if the desired logic cannot be expressed using the other methods provided by Experiment.

Parameters:

run (RunDefinition) – the RunDefinition instance to mutate.

Return type:

None

get_default_analyze_function()#

Returns default analyze function.

The analyze function can be either a full analyze function, in which case it should have the arguments [components, run_result, **kwargs], and it should perform the whole analysis for the experiment.

You can also provide a group analyze function, which can have any combination of the following arguments, which will be passed in automatically:

  • group: Mandatory. (ComponentGrouping) The parallel group for the iteration.

  • analyze_result: (AnalyzeResult) Contains the dataset and all metadata.

    Can be mutated iteratively to generate analysis.

  • run_result: (RunResult) Contains the dataset and all metadata.

  • chip_topology: (ChipTopology) The chip topology data structure.

  • settings: (SettingNode) The settings tree used in the run. Also contained in result.

  • data_color: (xarray.Dataset) The data for the color group of this component group.

  • circuit_index: (int) Index of the color group.

A group analyze function can return either

  • a new AnalyzeResult object, the contents of which will be merged with results from other iterations, or

  • None. This is sufficient if result is passed as an argument and mutated by the function.

The default behaviour of this method just returns the function stored in default_analyze_function, but it can be overridden if more complex behaviour is needed.

Return type:

Callable[[…], AnalyzeResult | None]

analyze(components=None, run_index=-1, analyze_function=None, **kwargs)#

Analyzes an experiment run and returns the result.

Based on the used analyze function (either the one returned by get_default_analyze_function() or the argument analyze_function), it will either just apply the function to the run result specified by run_index (full analyze function) or loop through the parallelly runnable partitions of the QPU (colours) and further the parallel groups within, building the full analyze result iteratively (group analyze function). The former and latter cases are automatically detected by inspection the signature of the provided analyze function.

Note

Overriding this method is allowed for backwards compatibility, but will be restricted in the future.

Parameters:

  • components (ComponentGrouping | None) – limit the analysis to these components.

  • run_index (int) – The run index.

  • analyze_function (Callable[[...], AnalyzeResult | None] | None) – function for performing the analysis. See get_default_analyze_function() for more info.

  • kwargs – Additional arguments for analyze_function.

Returns:

The analyze result.

Return type:

AnalyzeResult

final create(components=None, default_sweep_ranges=None, sweeps=None, settings=None, context=None)#

Create a complete RunDefinition for a new run.

This method formulates the complete definition of the run from user inputs. It is used when an experiment is run, and defines the arguments accepted by run(). create can be called manually to inspect the content of the RunDefinition.

Parameters:

  • components (list[str] | list[tuple[str, ...]] | list[list[tuple[str, ...]]] | None) – The names of the “computational” components for the experiment. Typically, this means the qubits that are involved in the playlist generation, but in specific experiments this could be anything else as well (e.g. the couplers or some combination of the couplers and qubits). The components can be given as a flat list, a grouped list (list of tuples) or as an already partitioned list (i.e. “colour groups”) of lists of tuples.

  • default_sweep_ranges (list[None | SweepOptions | ndarray | tuple[SweepOptions | ndarray]] | dict[str | Parameter, SweepOptions | ndarray] | None) – New ranges for the default sweeps. These values replace the sweep.options defined in the sweeps in get_default_sweeps().

  • sweeps (list[Sweep | tuple[Sweep, ...]] | None) – Additional user-defined sweeps.

  • settings (SettingNode | None) – All settings to set before sweeping. By default, uses the return value of get_settings() when called without arguments.

  • context (dict[str, Any] | None) – Optional custom Compiler context.

Returns:

A definition for a new run and the Compiler context.

Return type:

ExperimentDefinition

final submit_run(exp_definition)#

Submit an experiment for execution on Station Control, wait for the results and post-process them.

ExperimentDefinition.run_definition.additional_run_properties is recorded in the database.

Note

Experiment does not currently support stateful effects recorded in the Compiler context to be used when post-processing the return data. The reason is that Experiment runs need to be loadable from the DB such that the post-processing is applicable. The Compiler context is not generally serializable, so relying on data stored in it during the compilation (before execution) would break the loadability. Therefore, an empty context is used for the post-processing (the post-processing stages can still be stateful and utilize the context, but they cannot rely on information stored during the pre-execution compilation).

Parameters:

final static get_by_run_id(run_id)#

Get an instance of the Experiment that produced run_id, holding its run result.

This method is for accessing legacy data. To access runs sumbitted via IQM Server, use get_by_job_id().

If the name of the experiment in the database does not match any currently imported Experiment class, will try to load and post-process the data using the base class Experiment. In this case, the experiment-specific analysis is not available. If the post-processing also fails, a stub Experiment containing only the raw data is returned.

Note

The old result is loaded from an EXA database, so you must initialize EXA with a connection to the database that holds your run. In most on-premises installations there is just one shared database that is automatically accessed through STATION_CONTROL_SERVICE_URL or IQM_SERVER_URL.

Warning

The returned Experiment instance should only be used to view and analyze old run data, not execute new runs, since it refers to the station that produced the old run, and not necessarily the station you’re connected to. If you want to execute new runs, create another instance of the correct Experiment subclass and use it instead.

Parameters:

run_id (UUID) – ID of a run that exists in the database.

Returns:

An instance of the Experiment subclass that produced run_id. The dataset is accessible through the last_run attribute.

Return type:

Experiment
